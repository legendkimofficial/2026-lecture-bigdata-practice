# Week 5 관찰 기록

## Task 1 — PageRank와 두 실패 사례
- 고장 난 버전에서는 dead end의 rank가 다음 벡터로 전달되지 않아 총합이 0으로 소실된다. 정상 버전에서는 해당 질량을 모든 노드에 균등 재분배했으며, 공식 dead-end 검사에서 총합 1을 보존했다.
- dead end에서는 균등한 재출발로 질량 소실을 막고, spider trap에서는 teleport로 탈출 경로를 만들어 두 문제를 처리했다. 단순히 남은 rank를 정규화하는 것으로는 trap 문제를 해결할 수 없다.
- beta는 링크를 따라갈 확률이며, 1−beta의 확률로 전체 노드 중 하나를 균등하게 선택한다. 고장 난 trap에서는 C+D가 1이지만, beta=0.85인 정상 버전에서는 A·B에도 양의 rank가 남았다.

## Task 2 — 수렴 비용과 순위 안정성
- tol=1e-10에서 beta 0.5→0.99에 따라 1,200개 그래프의 반복 횟수는 14→24회였다. teleport가 줄면 수축이 느려질 수 있지만 실제 증가폭은 그래프 구조에 좌우된다. beta=0.85의 tol을 1e-6→1e-10으로 줄이면 12→20회로, 추가 한 자리당 평균 2회가 필요했다.
- 그래프를 1,200→6,000개로 5배 늘렸을 때 beta=0.85에서 20→22회, 중앙 실행 시간은 0.014979→0.092434초(6.17배)였다. 반복 횟수는 혼합 속도에, 시간은 반복당 노드·간선 처리량에도 영향을 받는다. CPU i5-8500, RAM 15.95 GiB, Python 3.12.14이며 실행 프로그램과 원시 120회 측정은 convergence.json/md에 기록했다.
- 두 크기 모두 처음 순서가 달라진 측정 beta는 0.7이었다(p00000·p00004의 7·8위 교환). 상위 10개 구성원은 같았지만 순서는 beta에 의존하므로, 발표된 순위의 설정을 확인해야 한다. 정확한 순위 교차점까지 측정한 것은 아니다.

## Task 3 — 희소 구현과 dense 결과 비교
- n×n 행렬 대신 정수 목적지·차수의 인접 목록 O(n+E)와 rank 벡터 두 개를 사용했다. float 저장량은 임시 스칼라 여유분까지 보수적으로 2n+16개로 셌으며, n=1,200에서 2,416개로 dense의 1,440,000개보다 약 596배 적었다. 이는 float 개수 비교이며 Python 객체·정수 인접 목록을 포함한 전체 RAM 배율은 아니다.
- teleport와 dead-end 재분배는 모든 노드에 같은 스칼라 `(1−beta+beta·dangling_mass)/n`를 더하면 된다. O(n) 벡터 초기화와 O(E) 링크 분배만 필요하므로 O(n²) 행렬을 만들 필요가 없다.
- 변경하지 않은 bench.py에서 1.01초→0.01초(반올림 전 시간 기준 81.3배)로 strong 기준을 만족했고, 노드별 최대 차이는 1.18e-15로 1e-9 이내였다. 이 작은 차이는 dense와 sparse가 부동소수점 덧셈·곱셈을 수행하는 순서가 다르기 때문이다.
