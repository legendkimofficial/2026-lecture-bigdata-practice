# Week 3 관찰 기록

## Task 1 — MinHash와 LSH
- 행별로 1이 있는 열의 목록을 준비한 뒤 각 행을 한 번씩 처리하여, 같은 행의 해시값을 모든 해당 열에 재사용했다. 열마다 전체 행을 다시 읽는 작업을 피하며, 현재 집합 기반 입력을 뒤집는 인덱스에는 O(nnz)의 추가 메모리가 든다.
- 서명 길이가 밴드 수로 나누어떨어지지 않으면 ValueError를 발생시키도록 했다. 일부 서명 행을 버리거나 밴드 크기를 다르게 만들어 충돌 확률을 바꾸지 않기 위해서다.
- S1–S4의 실제 Jaccard는 2/3이지만 해시 2개의 일치율은 1이었다. 해시 수를 늘리면 이상적 MinHash의 표본 오차가 대략 1/√h로 줄어들지만, 서명 저장 공간과 최소값 갱신 비용은 늘어난다.

## Task 2 — 크기에 따른 성능과 교차점
- AMD Ryzen 7 9800X3D 8-Core Processor, RAM 31.15 GiB, Windows/Python 3.13.15에서 직접 측정했다. 이번 교차 구간은 n=625~750이며, LSH가 처음 이긴 측정점은 750개였다. 작은 입력에서는 행 인덱스·120개 해시·밴드 버킷을 준비하는 비용이 비교 절감량보다 컸다.
- n을 두 배씩 늘렸을 때 전수 비교 시간은 3.84, 4.21, 4.08, 4.06, 4.00, 4.22배가 되어 대체로 이차 증가를 확인했다. 정확한 시간·비교 수·메모리 표와 측정 범위는 curve.md에 정리했다.
- n=8,000에서 전수 비교 147.37초가 60초 대기 기준을 넘었다(LSH 3.84초). 먼저 문제가 된 것은 시간이며, 추가 peak 할당은 각각 0.0651 MiB와 31.7464 MiB였다. 입력 문서 메모리는 제외했고, 다른 사용자 앱의 부하는 확인하지 못했다.

## Task 3 — 비교 절감과 정확도
- h=120, b=30, r=4를 선택했다. 후보 확률 1−(1−s^r)^b에서 근사 전이 위치는 (1/30)^(1/4)=0.4273로 임계값 0.6보다 낮고, s=0.6에서 후보 확률은 98.45%다. 누락을 줄이는 쪽으로 설정했으며, 후보가 늘어나는 비용은 실제 Jaccard 검증으로 처리했다.
- 공식 데이터의 정답 121쌍을 모두 찾았고 recall/precision은 100%/100%, 비교는 2,246,140회에서 122회로 99.9946% 감소했다. 해시 수를 유지하고 b=12, r=10으로 바꾸면 전이 위치가 0.7800, s=0.6의 후보 확률이 7.02%가 되어 실제 recall이 48.76%(59/121쌍)로 하락했다(parameters.json).
- 비교 횟수 점수에는 해시 계산이 빠져 있지만 실제 시간에는 포함된다. 작은 입력에서는 전처리가 지배적이고, 큰 입력에서는 O(h×nnz) 갱신과 O(h×문서 수) 서명 저장이 부담이다. 예를 들어 문서 100만 개×120개 서명은 값만 64비트로 저장해도 약 0.96 GB이며 Python 객체·인덱스까지 포함하면 더 커진다. 위 확률은 이상적인 독립 MinHash 모형의 근사이며, 한 시드에서 얻은 recall 100%가 모든 데이터에서 보장되지는 않는다.
