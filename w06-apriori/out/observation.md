# Week 6 관찰 기록

## Task 1 — A-Priori와 confidence/lift
- seed 246의 20,000 baskets에서 support 50을 적용하면 2,000개 중 1,849개 항목이 살아남는다. 가능한 쌍의 상한은 brute force의 1,999,000개에서 1,708,476개로 줄며, 실제로 함께 나타나 할당된 기준 counter는 820,259개였다. pass two에서는 생존 항목끼리만 조합했다.
- 가장 높은 confidence 규칙은 1468→0으로 52/62=83.871%지만 역방향 0→1468은 52/13,080=0.39755%다. 항목 1468을 산 사람에게 0을 제안하는 방향이 조건부 확률상 유용하며, 역방향 주장은 거의 성립하지 않는다.
- 이 규칙의 lift는 1.28243이다. 항목 0의 기본 등장률부터 65.4%이므로 confidence만큼 강한 관계는 아니며, 동시 등장 52회로 threshold 50에 가깝다는 점도 고려해야 한다. 작은 검증 데이터의 diaper→beer도 confidence 0.8에 lift 1.12로 인기도의 영향을 보여 준다.

## Task 2 — Support 감소, 후보 수와 답의 차이
- 기본 데이터는 support 1까지 완료됐고 최종 결과를 포함한 추적 peak는 311.88 MiB였다. 별도 확장 데이터(60,000 baskets·20,000 items·AVG=30)는 support 50에서 counter 2,797,537개, 390.33 MiB, 10.73초로 중단했다. 바구니 사이에 확인하는 256 MiB 메모리 작업 예산이 먼저 걸렸으며, dict resize로 초과한 값이고 실제 OS OOM은 아니다.
- 기본 support 400→200→100→50에서 counter는 5.54→4.67→3.00배씩 늘어 단순 두 배보다 빨랐다. 그러나 support 25에서 모든 항목이 살아남은 뒤에는 관측 쌍 893,456개로 포화됐다. CPU i5-8500, RAM 15.95 GiB, Python 3.12.14이며, 동시 실행 앱·원시 13행·측정 범위는 explosion.json/md에 기록했다.
- support 50은 counter 820,259개로 답 6,397개를 찾는 128.23배의 간격이 있었다. 25→1에서는 counter가 그대로인데 답은 17,045→893,456개로 52.42배 늘어 답이 항상 천천히 증가하는 것은 아니었다. 후보 저장의 낭비와 답 자체의 저장 비용을 구분해야 한다.

## Task 3 — PCY의 필터 효과와 실제 메모리
- 충돌을 줄이기 위해 1,048,576 buckets를 선택하고 pass one의 정수 배열을 실제 1-bit bitmap으로 바꾼 뒤 해제했다. 변경하지 않은 bench.py에서 답 6,397개의 support까지 같았고 최대 counter는 820,259→13,357개로 98.37% 감소했다.
- bucket 배열 4,194,384 B와 bitmap 131,129 B가 변환 중 공존하므로 약 4.13 MiB에 항목 메타데이터까지 필요하다. 입력 생성 후 추적한 실제 peak는 baseline 97.55→PCY 4.45 MiB였다(RSS는 아님). 같은 2,000개 상품·support 50에서 첫 N개 baskets를 쓰면 3,000개에서는 PCY가 더 크고 5,000개에서는 더 작아 교차 구간은 그 사이였으며, 상품 수·support·충돌률·객체 비용에 따라 달라진다.
- bucket을 65,536개로 줄이자 배열은 262,224 B로 작아졌지만 충돌이 많아져 counter가 313,855개로 늘고 감소율은 61.74%로 떨어졌다. 답은 그대로였으며, 작은 bucket 배열이 전체 메모리까지 항상 절약해 주는 것은 아니다. 상세 byte 측정과 재현 방법은 pcy.md 및 pcy_experiments.json에 있다.
